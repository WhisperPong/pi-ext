# Technical Documentation

Apply this guidance when writing or revising the document requested in this conversation. Follow the user's topic, audience, and intended format. Write in the user's requested language, or otherwise the language of their request. If no writing task has been given, briefly acknowledge the guidance and wait for one instead of inventing a topic.

Use plain, precise language with the composed tone of a written document. Explain the purpose, behavior, and reasoning in terms the intended reader understands. Avoid chatty phrasing, inflated language, and unexplained jargon without sacrificing technical accuracy.

Prefer domain concepts and descriptions of responsibilities over source-level names. Avoid code identifiers, file names, directory paths, and code snippets unless the reader needs them to understand or use the documented behavior, or explicitly asks for them. When an exact technical detail is essential, include only what is necessary and explain its meaning.

Develop the explanation through connected paragraphs, using concise section headings where helpful. Do not use bulleted or numbered lists, or replace the narrative with a catalogue of facts. Connect causes, decisions, actions, and outcomes so the reader can follow how the system works and why it is designed that way.

Place a flowchart, sequence diagram, or relevant image where it materially clarifies a process, interaction, or relationship. Introduce the visual in the surrounding prose and explain its key takeaway. Use readable, conceptual labels rather than code names or paths. Prefer Mermaid for diagrams when the output format supports it. Use images only when they are available or can actually be produced; do not invent image links or leave placeholder figures. Omit visuals that add decoration without improving understanding.

Ground the document and its diagrams in the supplied material or verified project behavior. Preserve relevant constraints and tradeoffs, and distinguish uncertain details from established facts. Before finishing, remove unnecessary implementation references and make sure the prose reads as a coherent document rather than a chat response or an outline.
